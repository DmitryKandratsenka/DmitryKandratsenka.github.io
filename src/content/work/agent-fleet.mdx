## The problem

In August 2026 I started Spoonbill, an invoicing product for Germany, Austria and Switzerland, next to a full-time job and a second product, Sklad. Invoicing is not a weekend app. It has tax law in it, e-invoice formats a government validates, a web app, an iOS app and a landing site in seven languages.

One person cannot write all of that. A team of agents can, if someone designs how that team works. Picking the model and writing the prompts was the easy part. The hard part was the operating model: who may do what, how two workers avoid the same task, when a run stops, what counts as proof, and when a human has to decide.

## The system

Thirty scheduled routines run on one Mac: 21 for Spoonbill, 8 for Sklad and one for the machine itself. Each owns a **lane**: web developer, code reviewer, designer, mobile developer, mobile reviewer, QA, triage, design audits, SEO, marketing, and a weekly "accountant" that checks one country's legal wording against its primary sources.

They share one checkout, one GitHub board and three Slack channels. Everything they need to agree on lives in one rules file that every run reads. Its first section, the core, fits on two screens.

## Decisions that made it work

<Decision n="01" title="Lanes with written merge authority, not one agent that does everything" tradeoff="More routines to keep in step. The fix is one shared rules file, and a rule for the file itself: adding a lesson means removing or merging one.">

Developers never merge. The code reviewer merges web and API work on its own judgement, the mobile reviewer merges mobile work and starts the TestFlight build, and the designer merges its own design fixes.

I am asked only about a **completely new screen, or a change that moves data, touches money or cannot be undone**. That one sentence is most of the safety model.

</Decision>

<Decision n="02" title="Claims are git refs, so two runs never build the same ticket" tradeoff="A crashed run holds its claim until the TTL expires. TTLs are set no longer than the gap to the lane's next run, so a dead claim never blocks a full cycle.">

Before a run builds anything, it claims the ticket and its lane slot by pushing a ref to `origin`. A push either lands or it doesn't, so the remote is the lock, with no extra service. A second run of the same lane exits at once with code 10 and says so.

One script does the whole start: it makes a fresh worktree off `main`, claims the slot from inside it, reads the claim back and starts the clock. If any step fails, it undoes the others.

</Decision>

<Decision n="03" title="A clock, not a PR cap" tradeoff="A tight cap ends some good runs early. The data says that costs less than letting a few runs wander for hours.">

Every run has a work cap and an absolute cap. Past the first it claims nothing new; past the second, anything still running is presumed stuck unless the run can name its progress in the last five minutes. Neither cap kills a run, but each changes how careful it is.

</Decision>

<Decision n="04" title="Verify once, on the merge result, and keep CI almost empty" tradeoff="Correctness rests on the reviewer's machine and one gate script. That script posts a required status on GitHub, so main cannot take a merge it hasn't seen.">

Developers run only the specs their diff touches, by name, and prove each one red first. The reviewer runs the whole sweep once, on the merge result, and posts the `local-gate` status that `main` requires.

Cloud CI does almost nothing: it checks that a UI change links its screenshot, and runs the guards once a night. That keeps the bill flat however many PRs the fleet opens.

</Decision>

<Decision n="05" title="Deploys run on a timetable; production truth comes from a probe" tradeoff="A fix can wait up to four hours for its slot. A production regression is the one exception: QA wakes a hotfix routine, which ships at once.">

A merge deploys nothing. CircleCI ships `main` six times a day, at fixed UTC slots. Between 01:30 and 03:43 is **QA's quiet window**: no deploy runs and no other lane touches the iOS simulator, so the nightly regression tests a stable system.

Nothing is "live" because a tick went green. A probe checks the served bundle every 15 minutes and pages if a slot shipped nothing it owed.

</Decision>

<Decision n="06" title="The board is the memory. No handoffs, ever" tradeoff="Ticket hygiene costs tokens on every run. A run that forgets context would cost more.">

A run never leaves notes for the next one. Unfinished work and anything found along the way becomes a GitHub issue, filed in the run that found it, in a fixed shape under 150 words: *what happens, where the design is, why it matters, proof, done when*. Type and priority are GitHub fields, epics are sub-issue links, waits are `blocked by`.

A ticket a routine files can't be claimed until triage has looked at it, so the fleet can't feed itself work.

</Decision>

<Decision n="07" title="Every claim carries proof, and every question to me is one sentence">

Screenshots go to a dedicated `verification-media` branch and are linked from the PR. A UI change without its picture fails its check.

What reaches me in Slack is structured: a bold title, categories, one linked line each. A question is one plain sentence I can answer in a few words, from a phone notification. The evidence stays on the PR.

</Decision>

## What broke, and what I changed

Running it taught me more than designing it. Four lessons, each now written into the rules:

<Lesson title="Disk became the binding constraint, and it failed dishonestly">

Six worktrees a day at 1.3 GB each (2.4 GB for a mobile one) filled the volume to 100% on 29 August while two runs were live. The symptom was a test failure that looked like a code bug. Now every building run checks free space before it claims work, and the reclaim order is measured, not guessed.

</Lesson>

<Lesson title="A run that does not exit blocks the next one">

One day the scheduler recorded hundreds of skipped slots: previous runs still open, or too many routines live at once. One run had parked on a permission prompt. The rule now: a routine that is done ends its turn. It never waits.

</Lesson>

<Lesson title="The gaps were the problem, not the count">

On 5 September the fleet merged 46 pull requests, yet a PR opened at 10:40 waited eleven hours for a reviewer. I re-timed the lanes so every developer run has a reviewer run after it, and every deploy has a review before it.

</Lesson>

<Lesson title="Cadence follows the ledger">

Every run writes one line to a ledger: what it opened, merged and filed. When 13 of 32 reviewer runs found nothing to review, I cut runs. When 21 PRs piled up two weeks later, I added three back, at times that avoided the mobile reviewer.

</Lesson>

> The agents are the easy part. The work is the operating model: authority, contracts, clocks and evidence. It's the same work as leading a team of people, done in writing.

That's the skill I'd bring to a team: deciding what a group of capable workers may do on their own, and building the system that makes those decisions hold.
